# 잇데이 테스트/운영 완전 분리와 운영 반영 플로우

작성일: 2026-09-23  
상태: 적용 기준 문서. 운영 반영 전 차단표로 사용한다.

## 1. 결론

테스트와 운영은 “주소만 다르게 쓰는 것”으로는 부족하다. 앱, 서버, DB, 저장소, 결제, 외부 로그인, 비밀키, 배포 권한을 모두 나눠야 한다.

운영에 반영할 때는 아래 순서만 허용한다.

```text
개발 가지
  → 테스트 앱 설치
  → 테스트 서버
  → 테스트 DB
  → 테스트 결제/외부 로그인
  → 보안 확인표 통과
  → 운영 반영 승인
  → 운영 앱 빌드
  → 스토어 제출
  → 운영 확인
```

중간에 하나라도 `FAIL`, `NOT VERIFIED`, `BLOCKED`면 운영 반영을 멈춘다.

## 2. 절대 섞이면 안 되는 것

| 구분 | 테스트 | 운영 |
| --- | --- | --- |
| 앱 | 테스트용 설치 링크 또는 내부 배포 | App Store / Google Play 운영판 |
| 서버 | 테스트 서버만 | 운영 서버만 |
| DB | 가짜 고객·가짜 예약·가짜 결제 데이터 | 실제 가입자·실제 고객·실제 결제 데이터 |
| 파일 저장소 | 테스트 사진/첨부만 | 실제 고객 사진/첨부 |
| 결제 | 테스트 결제, 샌드박스, 승인 없는 결제 | 실제 결제 |
| 외부 로그인 | 테스트용 Google/Naver/Kakao/Instagram 설정 | 운영용 외부 로그인 설정 |
| 비밀키 | 테스트용 키 | 운영용 키 |
| 오류 재현 | 마음껏 가능. 단 가짜 데이터만 | 실제 장애 대응 외 금지 |

## 3. 환경별 원칙

### 로컬 개발

- 실제 고객 DB 연결 금지.
- 실제 결제 호출 금지.
- 개발자 개인 기기에서만 확인.
- 외부 로그인은 테스트 앱 설정만 사용.
- 고객 전화번호, 사진, 결제번호 같은 실제 자료를 넣지 않는다.

### 테스트 환경

- 테스트 앱은 운영 앱과 구분되는 설치 경로를 쓴다.
- 테스트 서버는 운영 서버와 분리한다.
- 테스트 DB는 운영 DB와 분리한다.
- 테스트 결제는 샌드박스만 쓴다.
- 테스트용 비밀키는 운영 비밀키와 완전히 다르게 만든다.
- 테스트 데이터는 가짜 이름, 가짜 전화번호, 가짜 사진만 쓴다.
- 운영 데이터 샘플이 꼭 필요하면 전화번호, 이메일, 사진, 결제번호, 외부 로그인 값, 메시지 내용을 모두 지운 뒤 복사한다.

### 운영 환경

- 운영에는 사람 고객, 실제 결제, 실제 외부 로그인이 붙는다.
- 운영 DB에 직접 실험 금지.
- 운영 배포 전에는 “어느 서버/DB/키를 물고 있는지”를 증거로 확인한다.
- 운영 장애 대응 외에는 운영 데이터 삭제·변경 테스트를 하지 않는다.

## 4. 운영 반영 차단표

운영 반영 전 아래 항목을 모두 채운다.

| 항목 | 통과 기준 | 현재 판정 |
| --- | --- | --- |
| 앱 내장 실행 | 앱 안에 실행 코드가 들어 있고 외부 GitHub Pages 주소에 의존하지 않음 | PASS: `scripts/guard-app-only-bundle.js` 존재 |
| Android 웹주소 실행 차단 | `server.url`이 없고 앱 실행 코드에 GitHub Pages 주소가 없음 | PASS: 검사 스크립트 기준 |
| Android HTTP 차단 | 암호화 안 된 HTTP 통신을 앱 설정에서 막음 | PASS: `usesCleartextTraffic=false`, `network_security_config.xml` |
| Android 백업 차단 | 앱 내부 민감 자료가 기기 백업에 섞이지 않음 | PASS: `android:allowBackup=false` |
| Android 디버그 차단 | 운영 앱에서 WebView 디버그 꺼짐 | PASS: `webContentsDebuggingEnabled=false` |
| Android 업로드 키 | 새 업로드 키가 Google Play에서 승인되어 새 빌드 업로드 가능 | BLOCKED: Google 승인 대기 |
| 테스트/운영 DB | Supabase 프로젝트 또는 스키마가 운영과 물리적으로 분리됨 | NOT VERIFIED |
| DB 권한 | 공개 테이블 전체 읽기/쓰기/삭제가 불가능함 | NOT VERIFIED: Supabase 보안 알림 재확인 필요 |
| 테스트/운영 결제 | 테스트 결제와 운영 결제가 키/가맹점/웹훅에서 분리됨 | NOT VERIFIED |
| 외부 로그인 | Google/Naver/Kakao/Instagram 테스트 앱과 운영 앱 설정이 분리됨 | NOT VERIFIED |
| 비밀키 | 운영 키가 앱 코드·저장소·로그에 없음 | NOT VERIFIED |
| 로그 | 전화번호, 이메일, 결제정보, 로그인값이 로그에 남지 않음 | NOT VERIFIED |
| 앱 위변조 방어 | Play Integrity 신호가 앱과 서버에 연결되어 있음 | PARTIAL: 콘솔 설정은 확인됨, 운영 요청 차단 적용 여부는 추가 확인 필요 |
| 재현 테스트 | 테스트 환경에서 로그인·고객·예약·결제·사진·외부 로그인 통과 | NOT VERIFIED |
| 운영 확인 | 스토어 설치판에서 실제 운영 주소, 운영 서버, 운영 DB 확인 | NOT VERIFIED |

## 5. Android 공식 보안 문서 반영 항목

Android 공식 문서의 핵심 내용을 잇데이에 이렇게 적용한다.

| 공식 문서 요지 | 잇데이 적용 |
| --- | --- |
| 앱 안에 API 키를 넣으면 앱을 뜯어서 볼 수 있음 | 앱에는 공개 가능한 값만 둔다. 서버 비밀키, 결제 비밀키, DB 최고권한 키는 서버/비밀 저장소에만 둔다. |
| 개발/테스트/운영 키를 나눠야 함 | 테스트와 운영 키를 완전히 분리하고, 한쪽 키가 털려도 다른 쪽을 폐기하지 않아도 되게 한다. |
| 키는 정기적으로 바꿔야 함 | 운영 키는 90일~6개월 단위 점검, 노출 의심 시 즉시 교체한다. |
| HTTPS를 사용해야 함 | HTTP 금지 설정을 유지하고, 서버 주소는 HTTPS만 허용한다. |
| 사용자 입력 검증 필요 | 앱 입력값만 믿지 않고 서버에서 한 번 더 검사한다. |
| 개인정보 접근·저장 최소화 | 전화번호, 고객 사진, 결제값, 외부 로그인값은 꼭 필요한 기간과 위치에만 보관한다. |
| 로그에 개인정보를 남기면 안 됨 | 운영 로그에서 전화번호, 이메일, 로그인값, 결제번호를 가린다. |
| WebView는 필요한 기능만 허용 | 앱 전용 번들 유지, 외부 웹주소 실행 금지, 불필요한 웹-앱 연결 다리 금지. |
| 외부에서 코드를 받아 실행하지 말 것 | 스토어 빌드는 GitHub Pages 같은 외부 웹 껍데기를 불러오지 않는다. |
| 다른 앱과 주고받는 통로는 닫거나 권한을 걸 것 | 꼭 필요한 딥링크만 열고, 나머지 컴포넌트는 밖에서 못 부르게 둔다. |

## 6. 실제 운영 반영 절차

### 1단계: 테스트 배포

1. 개발 가지에서 테스트 앱을 만든다.
2. 앱에 연결된 서버 주소, DB 주소, 결제 키, 외부 로그인 앱 ID를 출력 증거로 남긴다.
3. 테스트 앱을 원영님/테스터 기기에 설치한다.
4. 로그인, 고객 목록, 고객 상세, 예약, 매출, 사진 업로드, AI 캡션, 결제 준비, 외부 로그인 흐름을 테스트한다.
5. 테스트 중 만든 데이터가 테스트 DB에만 생겼는지 확인한다.

### 2단계: 보안 확인

1. Supabase 보안 알림이 0개인지 확인한다.
2. 공개 테이블에 권한이 켜져 있는지 확인한다.
3. 운영 비밀키가 앱 코드, GitHub, 빌드 결과물, 로그에 없는지 확인한다.
4. 결제 비밀키와 DB 최고권한 키가 앱에 들어가지 않았는지 확인한다.
5. Android 앱이 외부 웹주소를 불러오지 않는지 검사한다.
6. iPhone 앱도 외부 웹주소를 불러오지 않는지 검사한다.

### 3단계: 운영 반영 승인

1. 모든 항목이 `PASS`일 때만 운영 반영 승인.
2. 승인 전에는 운영 DB, 운영 결제, 운영 외부 로그인 설정을 건드리지 않는다.
3. 승인 뒤 운영 빌드를 새로 만든다.

### 4단계: 스토어 제출

1. iPhone은 App Store Connect에 새 빌드를 올린다.
2. Android는 Google Play 업로드 키 재설정 승인이 끝난 뒤 새 빌드를 올린다.
3. 심사 계정과 설명은 테스트용 개인정보가 없는 계정으로만 제공한다.
4. 심사 통과 전후로 빌드 번호, 서버 주소, DB 주소를 다시 확인한다.

### 5단계: 운영 확인

1. 스토어에서 직접 설치한다.
2. 로그인한다.
3. 운영 서버 `/health`와 운영 앱 빌드 번호를 확인한다.
4. 운영 DB에 테스트 데이터가 섞이지 않았는지 확인한다.
5. 결제는 실제 결제 전 승인된 최소 금액/테스트 상품으로만 확인한다.
6. 문제 발견 시 즉시 새 배포를 멈추고 이전 빌드로 되돌린다.

## 7. 자동으로 막아야 하는 규칙

아래는 사람이 실수하지 않게 자동 검사로 막는다.

- 앱 빌드 안에 GitHub Pages 실행 주소가 있으면 실패.
- Android/iPhone 설정에 외부 웹 실행 주소가 있으면 실패.
- 운영 빌드에서 테스트 서버 주소가 나오면 실패.
- 테스트 빌드에서 운영 서버 주소가 나오면 실패.
- 앱 코드 안에 결제 비밀키, DB 최고권한 키, 서버 비밀키가 있으면 실패.
- 운영 앱에서 HTTP 주소가 나오면 실패.
- 운영 앱에서 WebView 디버그가 켜져 있으면 실패.
- Supabase 공개 테이블 권한 경고가 있으면 실패.
- 테스트/운영 비밀키가 같은 값이면 실패.

## 8. 남은 실제 작업

지금 문서 기준으로 아직 끝났다고 말하면 안 되는 항목은 아래다.

1. Google Play 업로드 키 재설정 승인 대기.
2. 승인 후 Android 새 앱전용 빌드 업로드.
3. Supabase 보안 알림 재확인.
4. 테스트 DB와 운영 DB의 실제 분리 증거 확보.
5. 결제 테스트/운영 키 분리 증거 확보.
6. Google/Naver/Kakao/Instagram 테스트/운영 앱 설정 분리 증거 확보.
7. 운영 로그 개인정보 마스킹 확인.
8. iPhone/Android 스토어 설치판에서 실제 서버·DB 확인.

## 9. 원칙

“보안 완벽”이라고 말하지 않는다. 대신 아래처럼 판정한다.

- `PASS`: 지금 직접 확인했고 증거가 있다.
- `FAIL`: 문제가 확인됐다.
- `NOT VERIFIED`: 아직 확인하지 못했다.
- `BLOCKED`: 외부 승인, 계정 권한, 심사 대기 때문에 지금 못 한다.

이 방식으로 해야 “된 것”과 “아직 남은 것”이 섞이지 않는다.
