# 개인정보 사고 대응 절차

> 적용 대상: 잇데이 스튜디오 운영·스테이징의 고객 이름, 전화번호, 메모, 예약, 사진,
> Instagram 신원·댓글·DM, AI 입력·결과, 로그인 정보, 결제 관련 식별정보
>
> 최종 점검: 2026-09-16

## 1. 시작 기준과 담당

다음 중 하나라도 의심되면 이 절차를 즉시 시작한다.

- 다른 매장의 고객·예약·사진이 보임
- 고객 사진 또는 전화번호가 공개 주소나 잘못된 사용자에게 노출됨
- 로그인표, 외부 서비스 비밀키, 사진 임시 주소가 운영기록에 남음
- 탈퇴한 계정의 사진·고객 자료가 계속 열림
- Meta, Supabase, Google Cloud, AI 업체가 침해 가능성을 알림

최초 담당자는 Google Cloud의 `연준 (잇데이 장애 알림)` 채널로 알림을 받은 사람이다.
그 사람은 아래 표를 채우고, 기술 차단 담당자와 이용자 통지 담당자를 지정한다. 대체 담당자가
문서에 지정되어 있지 않으므로 정식 출시 전 이름·전화번호·대체 순서를 별도 내부 연락망에
등록해야 한다. 고객 개인정보를 이 저장소나 공개 이슈에 적지 않는다.

## 2. 처음 15분: 탐지와 확산 차단

1. 실제 개인정보를 넣지 않고 운영기록에 `[PRIVACY_INCIDENT] INC-...`를 남긴다. 이 문구는
   `privacy_incident_signal` 지표와 두 개의 알림 정책을 작동시킨다.
2. 영향을 받은 기능만 중단한다. 전체 서비스를 내리기 전에 사진 공개 주소, 잘못된 매장 접근,
   자동 DM 같은 직접 노출 경로를 먼저 막는다.
3. 노출된 사진 임시 주소를 폐기하고, 필요하면 Storage 객체 접근 정책 또는 객체 자체를 차단한다.
4. 계정 탈취 가능성이 있으면 해당 사용자의 서버 로그인표를 폐기하고 외부 로그인 연결을 해제한다.
5. 외부 서비스 비밀키가 노출됐으면 새 키를 발급하고 기존 키를 폐기한다. 공개 저장소의 문자열만
   지우는 것으로 끝내지 않는다.
6. 원본 운영기록은 보존하되 접근자를 최소화한다. 기록을 채팅, 공개 이슈, 이 저장소로 복사하지 않는다.

운영 전체 초기화, 전체 고객 삭제, 실제 고객 대상 시험 메시지, 증거가 담긴 운영기록 삭제는 금지한다.

## 3. 처음 60분: 범위 확인

다음 질문에 SQL 결과 숫자와 시각 범위로 답한다. 결과 행의 이름·전화번호·사진 주소는 보고서에
복사하지 않는다.

- 어떤 매장과 사용자가 영향을 받았는가?
- 이름, 전화번호, 메모, 예약, 사진, DM 중 어떤 항목인가?
- 최초 접근 시각과 마지막 접근 시각은 언제인가?
- 실제 열람·다운로드·발송이 있었는가, 단순히 접근 가능했는가?
- 웹, 모바일, Storage, Meta, AI 업체 중 어디까지 전달됐는가?
- 임시 사진 주소, 로그인표, 비밀키를 모두 폐기했는가?
- 같은 원인이 다른 매장에도 적용되는가?

Cloud Run 요청 식별자, 매장 내부 번호, 객체 내부 번호, 배포 버전만 사고 기록에 남긴다. 이메일,
전화번호, 메시지 본문, AI 입력, 전체 사진 주소는 가린다.

## 4. 복구와 확인

1. 최소 재현을 격리된 시험 매장과 합성 자료로 만든다.
2. 원인을 고치고 같은 문제를 잡는 자동 검사를 추가한다.
3. 다른 매장 접근, 삭제된 사진 접근, 오래된 로그인표, 같은 요청 반복을 다시 시험한다.
4. 수정 버전과 실제 제공 버전이 같은지 확인한다.
5. 노출 경로가 닫힌 뒤에도 외부 서비스의 복사본·캐시·백업 보관 여부를 확인한다.
6. 영향받은 이용자 목록은 통지에 필요한 최소 기간만 제한된 장소에 보관한 뒤 폐기한다.

서비스 재개 조건은 재현 경로 차단, 다른 매장 자료 0건, 폐기 대상 주소·로그인표 접근 실패,
새 검사 통과, 운영 감시 정상이다. 하나라도 확인되지 않으면 해당 기능은 계속 중단한다.

## 5. 이용자 통지와 신고

개인정보 보호법 시행령 제39조에 따라 개인정보 유출 등을 알게 된 경우 정보주체 통지는 원칙적으로
72시간 이내에 한다. 구체적인 항목이나 시점을 아직 모르면 확인된 내용, 피해 최소화 방법,
담당 연락처를 먼저 알리고 추가 확인 즉시 보완한다.

아래 중 하나이면 개인정보보호위원회 또는 지정기관 신고 대상인지 즉시 검토하며, 현재 공식 안내는
72시간 이내 신고를 요구한다.

- 1,000명 이상의 개인정보
- 민감정보 또는 고유식별정보
- 개인정보처리시스템이나 개인정보 처리 기기에 대한 외부 불법 접근

공식 신고: <https://brss.pipc.go.kr>

공식 기준: <https://pipc.go.kr/np/default/page.do?mCode=D030040000>

통지문에는 유출 항목·규모, 시점·경위, 회사의 조치, 이용자가 할 수 있는 조치, 구제 절차,
담당부서·연락처를 넣는다. 원인이나 범위를 추측해서 단정하지 않는다.

**LEGAL COUNSEL REVIEW REQUIRED:** 실제 사건의 통지·신고 의무, 예외 적용, 국외 업체 통보,
손해배상과 보존 의무는 사실관계에 따라 달라진다. 72시간 계산과 문안은 변호사 또는 개인정보
보호책임자의 확인을 받되, 그 확인을 기다리느라 기술 차단과 우선 통지를 늦추지 않는다.

## 6. 외부 업체 연락

| 업체 | 확인·요청 |
|---|---|
| Supabase | Storage·DB 접근 기록 보존, 잘못 공개된 객체 차단, 삭제·백업 보관 확인 |
| Google Cloud | Cloud Run·운영기록 접근 보존, 비밀키 교체, 영향 배포 확인 |
| Meta | 연결표 폐기, 잘못된 게시·댓글·DM 회수 가능성, webhook 재전송 확인 |
| AI/사진 처리 업체 | 입력·결과 보관 여부, 삭제 요청, 재학습 사용 여부, 처리 국가 확인 |
| Apple/Google | 결제·스토어 이용자 영향이 있을 때 신고·지원 경로 확인 |

업체 문의에는 사고 번호와 필요한 기술 식별자만 보내고 고객 사진·전화번호·메시지 원문을 다시
첨부하지 않는다.

## 7. 사후 작업

- 24시간 안에 현재 영향 범위와 남은 불확실성을 다시 확인한다.
- 7일 안에 원인, 탐지 지연, 차단 시간, 이용자 영향, 수정·검사·재발 방지 담당과 기한을 기록한다.
- 알림이 실제 담당자에게 도착했는지 분기마다 합성 사고 문구로 시험한다.
- 업체 삭제 확인서, 처리 국가, 보유기간, 재위탁 목록을 분기마다 갱신한다.
- 사고 문서의 고객 개인정보는 법적·분쟁 대응에 필요한 기간 뒤 안전하게 폐기한다.
