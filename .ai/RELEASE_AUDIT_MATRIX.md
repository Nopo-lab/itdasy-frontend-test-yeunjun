## §1. 기능 등급 (Critical / High / Medium / Low) — *무엇을 얼마나 깊게 파나*

등급은 **감사 깊이**를 정한다. 결함 심각도(§2)와 축이 다르다.

### 🔴 Critical — 틀리면 **돈·계정·법**이 걸린다
> 인증·권한 · 결제·구독·IAP · 회원권 · 예약확정

- **전 항목 필수.** §4 체크리스트 19개를 **하나도 스킵 안 함**.
- **동시성은 반드시 `Promise.all` 동시 100발**로 때린다. 순차 통과는 증거가 아니다.
- **DB 제약(UNIQUE·CHECK)까지 확인.** 애플리케이션 코드 방어는 방어선으로 안 친다.
- 실패 시 **출시 중단**.

### 🟠 High — 틀리면 **손님이 떠나거나 잘못된 메시지가 나간다**
> DM · 댓글응대 · 매출 · 고객 CRM · 잇비

- §4 체크리스트 중 **보안 4종(XSS·권한·IDOR·주입)과 Race** 필수.
- **발송류는 "두 번 나가나"를 최우선**으로 본다(재시도·멱등·큐 중복).
- 실패 시 출시 전 수정.

### 🟡 Medium — 틀리면 **원장님이 만든 게 없어진다**
> 작업실 · 연동 · 게시물

- **데이터 안전(저장·복원·기기간 동기화)과 되돌리기** 중심.
- 보안은 XSS만(입력이 LLM·화면을 거치므로).
- 실패 시 백로그 가능(단 '작업 소실'은 High 로 승격).

### 🟢 Low — 틀리면 **불편하다**
> UI·애니메이션·아이콘·카피·빈 화면

- 12축 중 UX동선·카피·접근성만.
- `TECH_DEBT.md` 한 줄로 충분.

> ⚠️ **승격 규칙 3개** — Low 라도 이러면 즉시 등급을 올린다:
> ① 원장님이 만든 데이터가 **사라진다** → High
> ② 안 되는데 **성공이라고 말한다**(거짓 토스트) → High (실제 사고: `app-save-file.js` 이전 상태)
> ③ 화면에 **손님 실명·연락처**가 새 나간다 → Critical

## §2. 결함 트리아지 (P0 / P1 / P2) — *찾은 걸 언제 고치나*

§1 등급은 **기능**에, P 등급은 **발견된 결함**에 붙인다. 둘은 대체로 같이 가지만 **항상 같지는 않다** — Critical 도메인에서 오타를 찾으면 P2 다.

정본 매트릭스는 `RELEASE_AUDIT_2026-07-31.md` §0.5(영향 × 발생가능성). 도메인 기본값만 여기 둔다:

| | 내용 | 도메인 |
|---|---|---|
| **P0** | 돈이 새거나 · 계정이 뚫리거나 · 심사가 막힌다 | 결제 · 회원권 · 예약 · 로그인 · 권한 |
| **P1** | 손님에게 잘못 나가거나 · 숫자가 틀린다 | DM · 댓글 · 매출 · 고객 · 잇비 |
| **P2** | 원장님이 불편하다 | 게시물 · 작업실 · 설정 · 연동 |

**적대검증(refute)을 통과한 발견만 매트릭스에 올린다.** 실측 근거: 2026-07-27 전수사냥에서 한 에이전트가 돈 관련 7건을 플래그했는데 **진짜는 1건**이었다.

### 🔬 증명 수준 L1~L4 — **P0 는 L3 이상만 허용**

| 등급 | 뜻 | 승격 조건 |
|---|---|---|
| **L4** | **실제 재현 완료** — 라이브·테스트 환경에서 공격/버그가 실제로 성공함 | 재현 절차와 관측된 결과를 적는다 |
| **L3** | **논리적으로 증명** — 코드 흐름만으로 **반드시** 성립. 외부 조건에 의존하지 않음 | 성립을 깨는 분기가 없음을 보인다 |
| **L2** | **강한 의심** — 코드상 가능하지만 **외부 조건 확인이 필요** (env·배포상태·플러그인·심사상태) | 그 조건을 확인하면 L3/L4 로 |
| **L1** | **후보** — 추가 검증 필요 | — |

**규칙**
1. **P0 는 L3 또는 L4 만.** L2 이하는 **P0 라고 쓰지 않는다** — `후보(L2)` 로 남긴다.
2. 모든 발견에 **등급과 그 등급인 이유**를 적는다. "왜 L4 가 아닌가"도 적는다.
3. L3 를 L4 로 올릴 수 있는 **구체적 재현 절차**를 아는 경우 같이 적는다.
4. 재현에 **자격증명 입력·계정 생성이 필요하면 하지 않는다.** L3 로 두고 절차만 넘긴다.

> 이유: "P0 인 줄 알았는데 아니었다"가 가장 비싼 실수다. 2026-07-27 라운드에서 7건 중 6건이 그랬다.

### 🧨 반증 시도 — **P0/L3 는 이걸 통과해야 남는다** (필수 절차)

P0 로 올린 **모든** 항목에 대해, 등급을 확정하기 전에 다음 4단계를 수행한다.
**독립된 3개 렌즈로 각각** 돌린다(한 사람이 한 번 훑는 걸로 대체 금지 — 자기 결론을 방어하게 된다).

| # | 단계 | 렌즈 |
|---|---|---|
| 1 | **이 취약점을 막는 다른 코드가 있는지 전역 검색** | *다른 가드* — 미들웨어·데코레이터·부트스크립트·SW·헬퍼까지. 있다고 가정하고 찾는다. 이름만 보고 판단 금지, 코드를 읽는다 |
| 2 | **다른 실행 경로가 존재하는지 찾는다** | *다른 경로* — 근거 사슬의 각 고리가 **유일한 경로인지** 호출처 전수로 확인. 주장이 놓친 추가 경로로 **더 심각해지는** 경우도 기록 |
| 3 | **무효화할 근거가 있으면 반드시 함께 기록** | *무효화 근거* — 죽은 코드/배포 제외/플래그 off/의도된 동작/이미 처리된 기록(git log)/전제 오류/영향 과대평가. **약한 근거도 적는다** |
| 4 | **반증에 실패했을 때만 L3 유지** | 하나라도 확실한 반증(근거 있는 high confidence)이면 → 오탐 또는 하향. 반증 실패했지만 외부 조건 확인이 필요하면 → **L2 하향(P0 자격 상실)** |

**규칙**
- **애매하면 반증 실패가 아니라 "확인 못 함"이다.** 반증은 확실할 때만 성공으로 친다. 그 반대도 같다 — 못 깼다고 해서 참이 증명된 건 아니다.
- 반증 결과를 **무비판적으로 믿지 않는다.** `refuted=true` 는 제시된 파일:줄을 **직접 열어** 재확인한다.
- 반증에 쓴 근거는 **살아남은 발견에도 같이 기록**한다 — 나중에 "왜 이게 P0 인가"를 다시 묻지 않게.

### 🚀 배포 검증 — **최신 revision ≠ 트래픽 받는 revision**

Cloud Run 에서 배포 확인할 때 흔히 놓친다.

```
❌ service 의 최신 revision 확인      = 운영 반영됐다   ← 틀림
   (service template 의 GIT_SHA 는 **실패한 배포**의 값을 보여줄 수 있다)
✅ traffic 100% 를 받는 revision 을 찾고 → 그 revision 의 SHA 를 확인
```

```bash
# 트래픽 받는 revision 만
gcloud run services describe <svc> --region=asia-northeast3 \
  --format='value(status.traffic[].revisionName,status.traffic[].percent)'
```

`"container failed to start"` 면 대개 내 커밋이 아니라 **alembic** 이다.
신종: 제약 마이그레이션이 **기존 데이터를 보고 raise** 하는 경우(→ 아래).

### 🗄️ DB 제약을 새로 걸 때 — 배포가 막히는 게 정상이다

제약(UNIQUE·CHECK·EXCLUDE)을 추가하면 **기존 데이터가 그걸 위반할 때 생성이 실패**하고,
`alembic upgrade head && uvicorn` 구조라 **컨테이너가 안 뜬다**(0022 에서 7연속 배포 실패).

| 하지 말 것 | 대신 |
|---|---|
| 마이그레이션이 데이터를 **자동 정리**해서 억지로 통과시키기 | **검사 → 목록 출력 → 중단.** 사람이 판단 |
| "일단 지우고 하나만 남기기" | 무엇이 지워졌는지 아무도 모르게 된다(0022 실제 사례) |
| 하드 삭제 | **soft delete** — 되돌리는 SQL 을 같이 남긴다 |

**절차**: 사전 점검 스크립트(읽기 전용) → 목록·영향도 확인 → 승인 → 정리 → 재점검 0건 → 적용 → 제약 존재 확인 → 실데이터 회귀.

**판정 팁**: 겹침·중복이 **동일 밀리초에 생성**됐으면 사람이 만든 게 아니라 **시드/임포트 스크립트**다.
`created_at` 을 반드시 같이 뽑아라 — "실제 고객 데이터"와 "테스트 데이터"를 가르는 가장 빠른 단서다.
반대로 **간격이 불규칙**(9초·25초·7초…)하고 값에 사람 말(욕설·"테스트")이 섞여 있으면 **손입력**이다.

### 🔢 마이그레이션은 **배포 먼저, DB 나중** (순서를 틀리면 배포가 막힌다)

```
❌ 틀린 순서 — 실제로 이렇게 해서 배포를 깨뜨렸다 (2026-08-03, 0035)
   로컬에서 alembic upgrade head   → DB 의 alembic_version = 0035
   그다음 커밋·푸시                → 그 사이 배포된 이미지엔 0035 파일이 없다
   → 컨테이너 부팅 시 alembic 이 "Can't locate revision '0035'" 로 exit(255)

✅ 맞는 순서
   커밋·푸시 → 배포(이미지에 마이그레이션 파일 포함) → 컨테이너가 스스로 upgrade
```

**왜 이런가**: `Dockerfile` 이 `alembic upgrade head && uvicorn` 이라 **컨테이너가 마이그레이션의 주체**다.
DB 만 앞서 나가면 이미지가 모르는 리비전을 만나 부팅이 실패한다. 반대(이미지가 앞섬)는 안전하다 —
그게 정상 배포 경로다.

**로컬에서 먼저 적용해야 한다면** 반드시 같은 커밋을 먼저 푸시하고 배포가 끝난 뒤에 하라.
서비스 자체는 안 죽는다(Cloud Run 이 실패 revision 에 트래픽을 안 넘긴다) — 하지만
**그 뒤의 모든 배포가 막힌다.**

### 🤔 도메인 종료 시 **"내가 틀릴 수 있는 이유" 최소 3개**

## §3. 페르소나 × 시나리오 — *누가 · 무엇을 하다가 깨지나*

### 3-1. 공통 페르소나 8 (모든 도메인에 적용)

| 페르소나 | 상태 | 이 사람에서만 터지는 것 |
|---|---|---|
| **신규 원장** | 가입 직후, 데이터 0 | 빈 화면·0으로 나누기·"3건 있어야" 안내 누락 |
| **기존 원장** | 데이터 수백 건 | 페이지네이션·느린 쿼리·목록 잘림 |
| **멤버십(유료)** | `plan = membership` | 한도 해제가 실제로 되나 |

## §5. 구현 여부 조사 파이프라인 — *진짜 되는 기능인가*

**이 앱에서 가장 많이 나온 결함 유형이 "있는 것처럼 보이는데 안 되는 기능"이다.** 순서대로 내려가다 끊기는 지점이 답이다.

```
프론트 버튼 있음
  ↓ 클릭 핸들러가 붙어 있나?          → 없으면: 장식용 버튼
백엔드 API 있음?
  ↓ @router 데코레이터 실재하나?      → 없으면: 404
라우팅 연결됨?
  ↓ main.py include_router 됐나?      → 없으면: 404
권한 있나?
  ↓ Depends(get_current_user) 있나?   → 없으면: 무인증 노출
DB 저장됨?
  ↓ commit() + 모델 컬럼 있나?        → 없으면: 새로고침하면 사라짐
실사용 가능?
  ↓ 플래그·env·심사로 잠겨 있나?      → 잠겼으면: 정직한 안내가 있나
Dead Code?  ← 호출하는 곳이 0개인가
Stub?       ← 함수는 있는데 pass / return None
TODO?       ← 주석만 있고 구현 없음
404 / NotImplemented?
```

### 확인 명령 (그대로 복사)

```bash
# 1) 프론트 버튼 → 핸들러
rg -n 'data-act="예약저장"' --type js
rg -n "on\('예약저장'|addEventListener" --type js

# 2) 백엔드 API 실재
rg -n '@router\.(get|post|patch|put|delete)' ../itdasy_backend-test/backend/routers/bookings.py

# 3) 라우팅 연결
rg -n 'include_router' ../itdasy_backend-test/backend/main.py | rg bookings

# 4) 권한
rg -n 'Depends\(get_current_user\)' ../itdasy_backend-test/backend/routers/bookings.py | wc -l

# 5) 죽은 코드 — 정의는 있는데 부르는 데가 없다
rg -n 'function _openFoo|_openFoo\s*=' --type js      # 정의
rg -n '_openFoo\(' --type js | wc -l                   # 호출 (1이면 정의뿐 = 죽음)

# 6) 스텁·TODO·미구현
rg -n 'TODO|FIXME|NotImplemented|pass\s*$|return None\s*$' \
   ../itdasy_backend-test/backend/routers/bookings.py
```

### ⚠️ 이 파이프라인이 실제로 잡은 것 (전부 라이브였다)

| 발견 | 끊긴 지점 |
|---|---|
| `auto_confirm` **예약 자동확정 토글** | 프론트 토글은 있는데 **백엔드가 아무것도 안 함** |
| `/persona/posts/ingest/instagram` | API 는 있는데 **아무도 호출 안 함** → 말투 학습이 시작조차 안 됨 |
| `getMyLayouts()` '내 레이아웃' | **항상 빈 목록** — 데이터를 만드는 코드가 main 에 없음 |
| 킬러 위젯 | 로드는 되는데 **붙을 컨테이너가 없어** 안 뜸 |
| `_markOffline` | **정의된 적 없는데 두 곳에서 호출** |
| 잇비 자동화 토글 | 실행 배관은 26 kind 지원인데 **enum 이 ~10개만 허용**해 나머지 잠김 |

> 🔑 **판정은 정규식 말고 실물로.** 스키마는 실DB, CSS 는 CSSOM, 죽은 코드는 AST·실행. `rg` 만으로 단정했다가 오판한 이력이 여러 건이다(`rg -r` 이 replace 로 먹은 사고 포함).

## §7. 실사용 하루 흐름 — *이어 붙였을 때도 되나*

한 기능씩 통과해도 **이어 붙이면 깨진다.** 페르소나별로 끝까지 태운다.

### A. 신규 미용실 원장 (첫날) — 🔴 Critical 경로
```
가입 → 샵 이름 입력 → 온보딩 → 인스타 연동(또는 건너뛰기)
  → 고객 추가 → 예약 생성 → 예약 확정
  → 회원권 판매 → 시술 완료 → 매출 등록(자동 전환)
  → 사진 업로드 → 레이아웃 → AI 캡션 → 발행
  → 로그아웃 → 재로그인(데이터 그대로인가)
```
**여기서 봐야 할 것:** 빈 데이터 화면 · 0으로 나누기 · "3건 있어야" 안내 · 온보딩 이탈 후 복귀.

### B. 기존 원장 (평일 하루) — 🟠 High 경로
```
아침 브리핑 확인 → 오늘 예약 확인 → DM 문의 답장(승인 발송)
  → 댓글 문의 공개 답글 → 손님 방문·시술 완료 → 매출 등록
  → 회원권 차감 → 노쇼 처리 → 저녁 게시물 작성·발행
  → 성과 확인
```
**여기서 봐야 할 것:** 발송 중복 · 숫자 정합(예약↔매출↔회원권) · 홈 카운트가 안 얼어붙나.

### C. 사고 상황 — 🔴 Critical 경로
```
지하철(신호 불안정)에서 예약 저장 → 실패 → 재시도
  → 서버 503 한 번 → (오프라인 배너 뜨나? 저장 잠기나?)
  → 회복 후 자동으로 풀리나 → 중복 저장 안 됐나
  → 폰과 PC 동시 접속 → 같은 예약 수정 → 어느 쪽이 이기나
  → 구독 만료 → 기능 잠김 → 기존 데이터는 보이나 → 결제 → 즉시 풀리나
```

## 🔌 동시성: `concurrency ≤ DB 커넥션 풀` (2026-08-04, 실측으로 배움)

> **"동시 N발 통과"는 인스턴스가 몇 개 떠 있었느냐에 따라 결과가 뒤집힌다.** 숫자만 보면 속는다.

### 규칙

    Cloud Run --concurrency  ≤  pool_size + max_overflow   (database.py)

인스턴스가 받는 동시 요청이 DB 커넥션 풀보다 크면 **초과분은 무조건 풀을 기다린다.**
`pool_timeout` 을 넘기면 500 이다. 매출·결제에서 이건 **돈 기록의 소실**이다.

### 실측 기록 (스테이징, POST /revenue)

| concurrency | pool | 동시 20발 | 동시 50발 | 판정 |
|---|---|---|---|---|
| 60 | 12 | — | **50건 전부 실패** | `QueuePool limit of size 8 overflow 4 reached` |
| 20 | 12 | 17/20, **32.9초** | 50/50, 1.3초 | 20 > 12 이라 여전히 초과. **절반만 고친 것** |
| **10** | 12 | 20/20, 0.6초 | 50/50, 1.1초 · 100발도 1.7초 | 10 ≤ 12 → 대기 없음 |

### 🚨 여기서 속기 쉬운 지점 두 개

1. **"50발은 통과했는데 20발이 실패"** — 모순처럼 보이지만 정상이다.
   50발은 Cloud Run 이 인스턴스를 3개로 늘려 커넥션이 36개가 됐고,
   20발은 concurrency 한계라 **인스턴스 1개에 그대로 몰렸다.**
   → **인스턴스 1개에 몰리는 회차(= concurrency 값과 같은 발수)가 진짜 시험이다.**
2. **첫 회차의 큰 지연은 콜드스타트다.** 10발 회차가 17.9초였지만 p50 은 0.62초였다.
   측정 전에 워밍업 요청을 한 번 쏘고, 중앙값과 최대를 같이 봐라.

### 검증 절차

    1) 워밍업 1발
    2) concurrency 값과 같은 발수로 때린다  ← 가장 중요
    3) 그 2배·5배·10배도 때린다
    4) 500 이 1건이라도 나오면 Cloud Run 로그에서 `QueuePool` 을 찾는다
    5) 끝나면 만든 데이터를 **전량 회수**하고 건수·합계가 기준선과 같은지 확인

### ⚠️ 실 DB 에 부하를 걸 때

- 만드는 레코드에 **회수용 마커**를 반드시 박는다 (`memo` 에 `[PERFTEST:<run>]` 등).
  중간에 죽어도 마커로 전부 찾아 지울 수 있다.
- **전역 rate limit 600/분(IP당, `main.py` `GLOBAL_RATE_LIMIT`)에 걸린다.**
  2026-08-04 에 3000건을 한 번에 밀다가 1822건이 429 로 튕기고, 그 뒤 회수 요청까지
  429 가 되어 **1178건이 DB 에 남았다.** 400건씩 끊고 사이에 45~60초를 쉬어라.
- 부하 테스트 중에 잰 화면 숫자는 **오염된 값**이다.
  (그날 홈 카드 전월대비가 테스트 데이터 때문에 12,477,000원 기준으로 계산됐다.)
  회수 완료 후 기준선 복구를 확인하고 **다시 재야** 한다.

## 💸 돈 도메인엔 감사 로그가 있어야 한다 (2026-08-04)

매출 삭제는 **hard delete** 였는데 성공 로그가 한 줄도 없었다.
남는 건 `DELETE /revenue/522 200` 뿐 — **얼마짜리였는지 어디에도 없다.**

기존 로그는 전부 예외 경로(멱등 재요청·동시 충돌·commit 실패)에만 있었다.
**정상 처리된 돈은 흔적이 없었다.** 사고가 나야 로그를 보는데, 그때 볼 게 없다.

돈을 만들고·바꾸고·지우는 경로에는 최소한 이걸 남긴다:

    user · id · 금액 · 결제수단 · 고객 · 시술 · 시각 · 연결된 예약 · 멱등키

- **삭제는 지우기 직전에** 찍는다. 그 로그가 그 레코드의 마지막 사본이다.
- 수정은 **값이 실제로 바뀐 것만.** 전부 찍으면 잡음이 되고, 잡음은 사고 때 안 읽힌다.
- 세 줄이 `id` 로 이어져야 한 건의 일생(생성→수정→삭제)이 추적된다.

## 🧪 감사 자체가 틀리는 3가지 (2026-08-04, 전부 실제로 겪음)

> 감사가 내는 FAIL 이 **코드 결함이 아니라 측정 결함**인 경우가 있다.
> 아래 셋은 이번 라운드에서 실제로 잘못된 판정을 냈던 것들이다.

### 1. 테스트 방식이 실사용 경로와 다르면 결론이 뒤집힌다

다중 탭 검증에서 `fetch()` 로 매출을 저장하고 "다른 탭이 낡은 값을 본다" 고 판정했다.
그런데 **실사용은 UI 버튼**이고, 그 경로는 `itdasy:data-changed` 를 쏴서 캐시를 지운다.
fetch 로는 그 이벤트가 안 난다 — **내가 만든 조건에서만 나는 버그**였다.

UI 로 다시 하니 캐시는 지워졌지만 **다른 탭 메모리는 그대로**여서 진짜 버그가 따로 있었다.
→ 잘못된 방법으로 찾은 자리에 진짜 버그가 있을 수도 있다. **경로를 실사용과 맞춘 뒤 다시 본다.**

### 2. 정리(cleanup) 조건을 넓게 잡으면 실데이터를 지운다

환불 E2E 후 `"환불" in service_name` 으로 회수했더니
**기존 회원권 해지 환불(id=610, -70,000원)까지 지워졌다.** 백업도 없었다.
감사 초반 기록해둔 값으로 복구했지만, 기록이 없었으면 잃었다.

→ **회수는 조건이 아니라 id 로.** 만들 때 id 를 모아두고 그것만 지운다.
   조건으로 지워야 한다면 **지울 목록을 먼저 출력**하고 눈으로 본 뒤 지운다.

### 3. 401 / 429 를 결함으로 오해한다

- 토큰이 exp 상 10시간 남았는데 서버가 401 → `users.min_valid_iat`(JWT kill-switch)로
  무효화된 것. **다른 세션이 같은 계정을 건드리면** 이렇게 된다.
  그 상태로 잰 "TTL 지나도 갱신 안 됨" 은 전부 무효였다.
- 성능 10만건 회차가 전 경로 429 → rate limit(600/분). 6경로×3회를 연속으로 때린 탓.
  **측정 실패지 성능 문제가 아니다.**

→ 측정이 이상하면 **먼저 자기 환경을 의심한다.** 토큰 유효성(`/auth/me`)과
   429 여부를 확인하기 전에는 코드 결함이라고 쓰지 않는다.

### 감사 중 실 DB 를 쓸 때 지킬 것

    1) 만드는 모든 행에 마커 + 만든 id 를 배열에 모은다
    2) 지울 땐 그 id 로만. 조건 삭제는 목록을 먼저 출력한다
    3) 감사 시작 시 기준선(건수·합계)을 적어두고, 끝날 때마다 대조한다
    4) 다른 세션이 같은 계정을 쓸 수 있다 — 감사 전용 계정을 따로 만든다

|---|---|---|---|---|---|

| summary(과거월) | 0.172 | 0.164 | 0.162 | 0.057 | **0.249** |

| 목록(전기간) | 0.116 | 0.350 | 1.397 | **3.317** (17MB) | 429(측정실패) |
| CSV zip | 0.155 | 0.290 | 0.974 | 2.241 | **3.185** |

### 읽는 법

- **summary 는 데이터량과 거의 무관하다** — DB 가 집계하기 때문이다. 10만 건에서도 0.73초.
  화면 히어로·홈 카드가 이걸 쓰므로 체감 성능은 안전하다.
- **목록만 응답 크기에 비례한다.** 페이지네이션이 없어서(`list_revenue` 가 `.all()`)
  건수만큼 그대로 내려온다. 100K 에서 한 달치가 8.3MB·2.9초.
- 100K = 1인샵이 하루 10건씩 **27년** 쌓은 양이다. 현실 규모(월 200건 → 연 2,400건)에서는
  전 경로가 0.2초 안쪽이다.
- 목록(전기간)의 100K 는 **측정 실패(429)** — 앞 요청들의 큰 응답으로 rate limit 에 걸렸다.
  그리고 이 경로는 **앱 화면이 호출하지 않는다**(기본이 period=month). 감사용 쿼리다.

### 측정할 때 지킬 것

- 경로당 1회 + 사이 간격(6초). 6경로×3회를 연속으로 때리면 429 로 전부 날아간다(실제로 겪음).
- 첫 회차 큰 값은 콜드스타트다. 중앙값과 최대를 같이 본다.
- 삽입은 `executemany` 로. 10만 건에 831초 걸린다 — 넉넉히 잡는다.
